# 归档与定时补传

每次发布先保存一份完整历史，包括标题、正文、附件副本和 SHA-256 校验值。归档完成后才开始平台上传；某个平台失败不会删掉已经保存的历史。

历史、账号、去重记录和计划属于当前工作区。“全选全部历史”仅选择此区的历史；补传仅能使用此区启用的插件。切换工作区不会暂停已提交的计划，详见 [多个工作区](workspaces.md)。

## 补传全部历史到平台

1. 打开“平台登录”，点击需要的平台的“登录”按钮。每个平台只使用一个账号。
2. 点击该平台旁的“补传历史”，进入历史页面，勾选“全选全部历史”，也可以只选择部分内容。
3. 选择“立即开始”或“指定时间开始”，填写每条历史的间隔。`0` 表示连续执行，`60` 表示每小时一条，`1440` 表示每天一条。
4. 点击“检查补传计划”，查看每条内容是否可补传、预计时间或跳过原因。
5. 点击“确认创建计划”。之后可在页面下方暂停、继续或取消，具体结果在“上传任务”查看。

账号是本机管理标识，Pixiv 可按账号配置 Cookie 登录，详见 [Pixiv 插件](../plugins/pixiv/README.md)。当前可用的“本地导出”将每个账号的结果放到独立目录，供完整验证流程。B站、小红书、Hugging Face、Civitai 保持待接入，不能执行云端补传。后续驱动接入并完成登录后，可复用现有历史与计划能力。

## 上传与重复规则

- 按归档时间从旧到新执行；同一请求中重复选择的归档只处理一次。
- 默认跳过目标平台已经成功上传的内容。其他平台的成功记录不会影响此平台。
- 默认也跳过目标平台正在排队、等待定时或执行中的内容，包括已暂停计划里的任务。
- 勾选“也重新上传已成功的历史”可以再次发布成功内容，但仍不会为同一账号重复排队。
- 检查时会列出不兼容或文件缺失的归档。确认创建时再检查一次，避免旧预览造成重复任务。
- 归档使用保存的文件副本，上传前核验 SHA-256；源文件移动、改名或删除不会影响已完成归档。归档副本损坏或丢失则不能补传。
- 上传失败可以单独重试，复用原归档；归档本身失败则需要重试归档，成功后再释放后续上传。

## 时间与重启

时间输入使用本机时区，存储使用 UTC 时间戳。开始时间是最早执行时间；队列繁忙时会顺延。间隔从前一条实际开始派发计算，不保证精确到秒，也不保证长任务完成的先后顺序。

计划需要应用正在运行。应用关闭、电脑关机或休眠时不执行；没有系统任务计划、托盘常驻或唤醒功能。重新打开后保留尚未开始的任务，并继续保持间隔。例如设置每小时一条，离线数天后也不会同时发出全部积压历史。间隔为 0 时允许按两个工作线程的并发能力连续执行。

暂停只影响尚未开始的任务，正在执行的任务继续完成。取消计划会取消未开始任务，并向正在执行的任务发出取消请求；已完成的上传不会被撤回。已经取消的计划不能恢复，但可重新创建补传计划。

运行中的任务遇到程序退出或崩溃，会标记为已中断，需要核对结果后手动重试；不会自动重复可能已经成功的远端发布。

## 本地保存位置

准确数据目录显示在“工作区管理”。以下为每个工作区内部的结构，新工作区位于根目录 `workspaces/<工作区 UUID>/`：

```text
upload-hub.sqlite3                  草稿、历史索引、账号标识、任务和计划
archives/<归档 ID>/                归档文件副本和 manifest.json
  manifest.json                    标题、正文、附件文件名和 SHA-256
  001_原文件名                      附件副本
deliveries/<账号 ID>/<任务 ID>/    本地导出驱动的独立输出
workspace.lock                     防止同一目录被多个应用实例同时调度
```

备份时关闭应用并保存整个数据目录。当前索引包含归档副本的绝对路径，还没有跨目录搬迁 / 重新导入功能。不要只备份数据库或手动删除归档文件。

旧版已成功的本地归档会自动纳入历史，无需重新复制；若旧副本已经丢失，仍显示历史记录，但检查会提示无法补传。

旧版本的空默认账号不会再作为独立选项出现；已有登录会自动沿用。Pixiv / X 按平台核对归档成功记录，避免旧账号标识造成重复补传。旧任务若仅因缺少账号配置失败，点击重试会使用当前平台已保存的登录。远端结果不确定的任务保留原提交记录，不自动改账号重发。
